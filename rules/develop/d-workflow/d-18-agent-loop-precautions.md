# D-18. 에이전트 자율 루프(/loop) 실행 주의사항

> **강제 규칙 (MUST)** — 이 케이스로 작업할 때 반드시 지킨다.
> - bootRun 프로세스를 강제종료(`Stop-Process -Force`, kill -9)하지 않는다 — PMX Oracle 세션 잔존→`ORA-18958`로 신규 DB 접속 전면 차단. 종료는 actuator shutdown 또는 Ctrl+C(SIGINT) graceful 방식만.
> - 수정 범위는 `bgt-fe`/`bgt-be` 로 제한한다 — `com`/`cst`/`PMS`/`TEMS`/`sp`/`bgt-be/docs/sp` 및 배포 SP(`PMX.PKG_*`)는 수정 금지, 원인이 배포 SP/인프라/권한이면 즉시 `BLOCKED` 마킹 후 다음 항목으로(→ §5).
> - 에이전트發 쓰기(기존행 수정/승인/삭제)는 auto-mode 분류기가 전부 차단하므로 우회하지 않는다 — 루프 시작 전 §0에서 (a)사전 권한 룰 / (b)사용자 조치 분리 / (c)읽기 간접검증 중 하나를 합의한다(→ §2).
> - 루프 착수 직후 환경 헬스체크(포트 7078/7070/3000, DB 신규접속, UI 가동)를 먼저 하고, `ORA-18958`이면 코드 디버깅 진입 금지(→ §3).
> - 쓰기 검증은 식별 접두어(예 `ZZ_LOOP_TEST`) 센티넬로만 하고 기존 실데이터는 수정/삭제하지 않는다. 환경 정리(포트 kill)는 모든 검증이 끝난 뒤 마지막에(→ §6, §7).

> **언제 쓰나** — 사용자 개입을 최소화하는 **자율 루프(/loop, hands-off)** 로 BGT 작업을 돌릴 때.
> 이 문서는 실제 `cntrct-ctrt` 마이그레이션 루프(2026-06)에서 **루프를 멈추거나 시간을 크게 잃은 사건들**을 근거로 한 재발 방지 런북이다. 추측이 아니라 발생한 사건 기준이다.

루프를 멈춘 원인은 코드가 아니라 ① 환경 안전(자초한 DB 장애) ② 권한(쓰기 차단) ③ 외부 SP 블로커였다. 따라서 **루프 시작 전에** 아래를 못박고 들어가야 헛돌지 않는다.

---

## 0. 루프 시작 전 합의 체크리스트 (필수, 착수 전에 확정)

루프를 시작하기 전에 다음을 사용자와 **명시적으로 합의**한다. 합의 없이 시작하면 매 항목마다 같은 벽에 부딪힌다.

- [ ] **쓰기 권한 정책** — 이 루프가 자율로 수정/승인/삭제(쓰기)를 해야 하는가? (→ §2)
- [ ] **BE 재기동 방식** — 누가, 어떻게 BE를 컴파일/재기동하는가? (→ §4)
- [ ] **검증 가능 범위** — 쓰기 검증이 권한상 불가하면, 어디까지 자율 검증하고 어디부터 사용자 조치 항목으로 분리하는가? (→ §2, §5)
- [ ] **금지 행동 인지** — §1을 읽었는가?

---

## 1. 절대 금지 (Hard Prohibitions)

| 금지 | 이유(실제 사건) |
| --- | --- |
| **bootRun 프로세스 강제종료** (`Stop-Process -Force`, kill -9 등) | BE를 강제종료 → PMX Oracle 세션 잔존 → 세션 한도 초과 → `ORA-18958`로 **모든 신규 DB 접속이 수 시간 거부** → 루프 전체 정지. 이번 루프 최대 손실. |
| **소스 수정 범위 이탈** | `bgt-fe`, `bgt-be` 만 수정. `com`/`cst`/`PMS`/`TEMS`/`sp`/`bgt-be/docs/sp` 는 수정 금지. (CLAUDE.md) |
| **배포 SP 수정 시도** | `PMX.PKG_*` 등 배포 프로시저는 못 고친다. 원인이 SP면 BLOCKED 진단만. (→ §5) |
| **분류기 차단 우회 시도** | auto-mode 쓰기 차단을 우회하려 들지 말 것. (→ §2) |
| **기존 실데이터 수정/삭제** | 쓰기 검증은 루프가 만든 센티넬로만. (→ §6) |

**BE 종료가 필요하면** graceful 방식만 사용한다: actuator shutdown 엔드포인트 또는 콘솔에서 Ctrl+C(SIGINT). 강제종료 금지.

---

## 2. 쓰기 검증은 현재 권한 구조상 hands-off 불가

auto-mode **분류기가 에이전트發 쓰기(기존행 수정 E-save / 승인 approval / 삭제 DELETE)를 전부 차단**한다(대화상 허락이 있어도). **신규 생성(N-save)과 읽기(list/detail)만 통과**한다.

→ 즉 **"hands-off"와 "쓰기 경로 검증"은 현재 설정에서 동시에 성립하지 않는다.**

루프 시작 전에 셋 중 하나를 합의한다:

- **(a) 사전 권한 룰**: 해당 엔드포인트 한정으로 settings에 권한 룰을 미리 추가 → 자율 쓰기 검증 가능.
- **(b) 사용자 조치 분리**: 쓰기 검증을 처음부터 "사용자 조치 항목"으로 빼고, 루프는 **거기서 멈추지 말고 다음 항목으로 진행**. 검증용 fetch 스니펫을 모아 한 번에 핸드오프.
- **(c) 읽기로 간접 검증**: 생성→목록/상세 재조회로 결과만 확인(쓰기 직접 검증 포기).

> 검증용 스니펫은 사용자가 브라우저 devtools 콘솔에서 직접 실행한다(라이브 세션 사용). 예:
> ```js
> fetch('/bgt/api/v1/bgt/cm/...', { method:'DELETE', credentials:'include' })
>   .then(r=>r.text()).then(t=>console.log(t));
> ```

## 3. 환경 헬스체크 (루프 시작 시 의무)

이번 루프는 DB가 죽은 걸 모르고 "코드 문제겠지"로 한참 헤맸다. **헬스체크 1회면 즉시 판별**된다.

루프 착수 직후 순서대로 확인:

1. **포트 가동** — BE(7078), com(7070), UI(3000)가 떠 있는가.
2. **DB 접속 1회** — 신규 접속이 되는가(`ORA-18958`이면 세션 잔존 의심 → 사용자/DBA 조치 대기, 코드 디버깅 진입 금지).
3. **검증 세션** — UI 가동 중인지(검증이 라이브 브라우저 세션에 의존하므로, UI가 내려가면 검증 불가).

헬스체크 실패 시 코드 작업으로 들어가지 말고 환경 복구를 먼저 한다.

---

## 4. BE 변경 = 재기동 라운드트립 최소화

BE 컴파일/재기동이 사용자 소유라 매 변경마다 핑퐁이 생긴다.

- **BE 수정은 모아서 한 번에** 적용 → 재기동 1회로 일괄 검증. diff 단위로 재기동을 요청하지 않는다.
- 재기동 방식은 §0에서 합의한 대로(누가/어떻게).
- FE 검증은 BE 무관하게 진행 가능: `npx yarn build:local` + `npx tsc --noEmit`.

---

## 5. 블로커 조기 분류 (막히면 즉시 판정)

이번 루프 W8(승인)은 결국 **배포 SP 자체 결함**(예외블록 주석처리)이라 수정 범위 밖이었는데, 늦게 깨달아 시간을 썼다.

막히면 항목 착수 직후 **한 번에 분류**한다:

- **(A) `bgt-fe`/`bgt-be` 안에서 고칠 수 있는가** → 고친다.
- **(B) 배포 SP / 인프라 / 권한 문제인가** → 즉시 `BLOCKED` 마킹 + **정밀 진단만** 기록 + **다음 항목으로**. 같은 벽을 반복 시도하지 않는다.

판정 기준: 변경해야 할 파일이 수정 범위(`bgt-fe`/`bgt-be`) 밖이면 (B)다.

---

## 6. 센티넬 라이프사이클

쓰기 검증은 **루프가 만든 센티넬 레코드로만** 한다(기존 실데이터 금지).

- 센티넬은 식별 가능한 접두어를 쓴다(예: 계약명 `ZZ_LOOP_TEST`).
- 생성한 센티넬의 **PK를 추적 목록으로 남긴다**.
- 항목 종료 시 삭제로 정리한다. 단 **삭제가 §2 분류기에 막히면** 정리를 사용자 조치 항목으로 넘기고, 애초에 **센티넬 생성을 최소화**한다(공유 DB에 잔존 위험).

---

## 7. 검증 경로의 취약성

검증을 **Playwright in-page fetch(라이브 브라우저 세션)** 에 의존하면 깨지기 쉽다(브라우저 세션·com 프록시 `/bgt`·UI 가동에 묶임 — 포트를 정리하면 검증 수단도 같이 사라짐).

- 검증은 **UI 가동 중에만 가능**함을 루프 전제로 명시한다.
- 환경 정리(포트 kill 등)는 **모든 검증이 끝난 뒤** 마지막에 한다.

## 8. 상태 기록

- 루프 진행 상태는 단일 문서(`docs/migration/<화면>/loop-progress.md`)에 모은다.
- 상단에 **사용자 조치 항목**(권한 밖/분류기 차단)과 **잔여 코드 To-Do**를 분리해 둔다.
- 커밋하지 않는다(명시 지시 없는 한). 파일 수정 + 진행 문서만.
